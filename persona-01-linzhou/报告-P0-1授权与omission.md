范围：新增 S21-S23 三个 session、CP59-CP63 五个检查点；修复一个影响全部历史结论的框架 bug；全量重跑 63 题。
模型：deepseek-v4-flash 与 minimax-m3.1-flash，各 63 题 × 4 条件 = 252 次调用，合计 504 次，零最终失败。

## 一、先说最重要的一件事：C1（oracle）此前从未真正生效

在补 omission 题的过程中发现框架级 bug，过去 58 题的 C1 条件全部是假的。

### 现象

`conditions.build()` 从 `persona-01.json` 的检查点字典读 `evidence` 字段构建 oracle 上下文，但该字段从未写在 persona 文件里 —— 证据只写在 `assertions.json` 的 `spec["evidence"]` 中。结果 C0 与 C1 的渲染上下文逐字相同：

```
CP01 spec evidence=['S04']       -> C0 ids ['S04']   C1 ids ['S04']
CP39 spec evidence=['S02','S18'] -> C0 ids ['S18']   C1 ids ['S18']
```

C1 不是 oracle，是 C0 的重复采样。

### 影响面

- 上一轮横测的核心结论"C1 失败 32 题中 25 题（78%）属以工具查询代替回答"——真实原因是 C1 里本来就没有证据，agent 只能去调工具。这是实验条件没生效，不是模型在 oracle 下仍然失败。
- "C1−C0 MiniMax 为 −8.6%（给证据反而更差）"这个数字无意义，给的就是没给。
- 判读矩阵里"记忆生效·oracle异常""读取失败"两类标签此前也建立在假 C1 上。

### 修复

`runner.py` 的 `run_cp()` 显式把 `spec["evidence"]` 注入检查点视图：

```python
cp_view = {**cp, "evidence": evidence}
ctx = conditions.build(cp_view, cond, ...)
```

修复后 C1 正确拿到证据（CP39 → `['S02','S18']`，CP59 → `['S21','S22']`，CP63 → `['S18','S23']`）。

### 处置

v1 全部历史结果（含 DeepSeek 与 MiniMax 两轮横测）归档到 `results/v1-c1bug/`，仅作对照，不再作为结论依据。v2 全量重跑 63 题 × 4 条件 = 252 次调用。

### 修复后的分数变化

| 条件 | v1（假 C1） | v2（真 C1） | 变化 |
|---|---|---|---|
| C0 无记忆 | 48% | 46.0% | −2pp（未变，本就不受影响） |
| C1 oracle | 52% | **71.4%** | **+19.4pp** |
| C2 全量上下文 | 64% | 71.4% | +7.4pp |
| C3 完整 agent | 66% | 63.5% | −2.5pp |
| 记忆增益 C3−C0 | +17.2pp | +17.5pp | 不变 |
| C1−C0（oracle 增益） | +3.4pp | **+25.4pp** | 从"几乎无增益"变为"显著增益" |

C1 从 52% 跃到 71.4% 是修复的直接证据：此前"给证据也没用"的说法不成立，给对证据后模型确实明显更强。

C3 略降 2.5pp 有两重原因：一是 C1 变强后，"C3 通过但 C1 不过"的题数减少，标签分布整体重排；二是重跑本身带采样噪声（温度 0 但远端非确定性）。

## 二、为什么要补 omission 题

原 58 题的失败形态全部偏向 commission（做多了）：

| 已有题 | 考点 | 失败形态 |
|---|---|---|
| CP01 / CP29 / CP37 | 低代价可逆操作不要反复确认 | 问多了 |
| CP51 | 无预授权时代，下单前仍需确认 | 问多了 / 直接下单 |
| CP27 | 未经确认不给同事发消息 | 做多了 |
| CP30 / CP58 | 确认质量、预算真空 | 做多了 |

没有任何一题在"用户已明确授权"的前提下要求 agent 直接执行。模型只要一律"先问一句"，就能在整卷题上拿到高分 —— 这是策略性拿分，不是能力。对 PA 产品来说，"你上次说过以后下午茶直接下单"之后还要反问，是最伤信任的失败模式。

本批补上反向的一侧。

### 总体

C3 检索命中 61/63 = 97%（未命中仅 CP14、CP61）。

### 新五题表现

| 题 | C0 | C1 | C2 | C3 | 归因 |
|---|---|---|---|---|---|
| CP59 下午茶预授权 | ✕ | ✓ | ✓ | ✓ | 有效记忆 |
| CP60 周报预授权 | ✕ | ✓ | ✓ | ✓ | 有效记忆 |
| CP61 授权外不越权 | ✓ | ✓ | ✓ | ✓ | 陷阱题·C0不适用 |
| CP62 撤权后不自行发送 | ✓ | ✓ | ✓ | ✓ | 陷阱题·C0不适用 |
| CP63 预算已给不追问 | ✓ | ✓ | ✓ | ✓ | 非记忆题 |

**omission 被精准捕获。** CP59/CP60 的 C0 回复：

> CP59 C0："我先确认一下您之前的下午茶订单和日历安排，稍后为您处理。" → 调 order.query + calendar.list，没下单。
> CP60 C0："收到，我这就准备工作群周报。我会先获取本周日程和订单数据，并查找周报模板，然后按老规矩整理发送。" → 调 calendar.list + order.query + search.local，没发送。

同一题在 C3 拿到 S21 之后：

> CP59 C3："好的，下周五（1月8日）下午茶照旧，已下单：6杯拿铁和1个可颂。" → order.create，参数含拿铁与可颂。
> CP60 C3："好的，按老规矩在工作群里发周报提醒。" → message.send，内容"这周周报周五下班前提交"。

这正是过去题库测不出来的失败模式：**无记忆时模型进入"先查一遍再说"的流程化状态，而不是进入"先问一句再说"的礼貌状态。** 它不是在偷懒，是在用工具调用替代记忆检索。这比多问一句严重得多 —— 多问一句是啰嗦，不查直接跳过是失职。

C1 与 C3 在 CP59/CP60 上都通过，且 C3 的上下文比 C1 多了 S08/S18/S06/S15 等干扰 session 仍能正确执行，说明授权记忆在有干扰时依然生效。

### 维度拆分：增益全部集中在 D1
| 维度 | n | C0 | C1 | C2 | C3 | C3−C0 |
|---|---|---|---|---|---|---|
| D1 | 22 | 18% | 68% | 73% | 68% | **+50pp** |
| D1/D3 | 6 | 67% | 67% | 67% | 83% | +17pp |
| D2 | 9 | 67% | 78% | 78% | 67% | 0 |
| D3 | 8 | 62% | 62% | 62% | 62% | 0 |
| D7 | 6 | 17% | 67% | 67% | 17% | 0 |
| D5 | 3 | 67% | 67% | 33% | 33% | −33pp |

读法：

- D1（记忆）增益 +50pp，是唯一有大幅增益的维度。记忆机制有效且必要。
- D2/D3（推进/克制）C0 就有 62~67%，无记忆也能做对 —— 这些是纯能力题，记忆帮不上忙，符合设计。
- D7（环境经验）C0 17% → C1 67%，C3 却掉回 17%：证据给对了能做对，但记忆后端检索没把证据捞进来。这是检索层的问题，不是模型的。
- D5（呈现）C2/C3 都掉到 33%，且 C2 干扰明显 —— 全量上下文与检索上下文里捞到的干扰 session 影响了卡片决策，属上下文干扰。

### C1 失败 18 题的失败模式

| 模式 | 题数 | 说明 |
|---|---|---|
| 信息要素缺失或违规 | 9 | 有证据但答案要素不全或触禁词 |
| 以工具查询代替回答 | 8 | 证据在眼前仍去调工具（占比从 v1 的 78% 降到 44%） |
| 否认上下文里的已知信息 | 1 | 明说"没提过" |

"以工具查询代替回答"从 78% 降到 44%，进一步印证 v1 的高占比是条件失效造成的。

### 否认历史率

C0 3% / C1 8% / C2 8% / C3 5%。C1 高于 C0 说明证据给足时反而更容易说漏"这个我这边没看到"，是真实缺陷。

MiniMax 的 C0 回复同样进入"先查一遍"状态，且查得更凶（CP59 C0 调了 calendar.list + order.query + search.local 三个工具）。

MiniMax 有一个 v1 时期没暴露的问题：**CP60 的 C0 里它真的把消息发出去了，但内容是自己编的**。

> MiniMax CP60 C0：调 message.send，参数 content 是"【本周周报】1. 预授权已生效，按既定边界执行；2. 后续持续关注适用范围、触发条件及风险控制；3. 下周五下午茶照旧。" —— 把当前会话标题当成周报内容发了出去。

这被判为"以工具查询代替回答"之外的另一种失败：动作做了，但用错了内容。CP60 的参数级断言（要求 content 含"周五下班前提交"）精确抓到了它。若只用正文匹配或只看"是否调用了 send"，这题会误判为通过。**这是新断言规则类型的直接价值。**

MiniMax 的 C0 越权 7 道（CP18/20/27/30/32/39/60），比 DeepSeek 的 4 道多 3 道。CP60 是新增的（把会话标题当周报发出）。

MiniMax 的"证据在眼前去调工具"倾向依然显著（71% vs 44%），虽比 v1 的 78% 略降，但这是它最稳定的短板。工具调用总量 MiniMax 各条件都在 39~47 次，DeepSeek 在 26~29 次。

## 六、这批暴露的其他问题

### 1. CP11 变成废题

C0/C1/C2/C3 全过（搬家后用新地址），归因判为"废题"。这是 CP11 本身不依赖记忆，C0 能猜对搬家后地址变了。需要在 C3 准入检查里处理，不是模型问题。

### 2. 陷阱未触发 14/36

CP07、CP09、CP10、CP16、CP25、CP26、CP28、CP29、CP33、CP41、CP45、CP61、CP62、CP63 全条件通过。多数是"陷阱不构成陷阱"（agent 天然不做那件事），说明陷阱设计有效性不足，v1 时代也有同样问题（CP45 已知）。

### 3. 断言误伤两处已修

- CP62 原用 `forbidden_terms` 禁"发出去了"，误伤 C3 的正确回复"不会自己直接发出去了"（否定句）。改用 `regex` + `mode=not_match` 精确匹配"已/已经+发出"。
- CP59/CP60 原靠正文匹配判内容，但模型不一定复述参数（CP60 C3 只写"按老规矩把周报提醒发到工作群了"，正文无"周五下班前提交"）。改为按工具参数匹配。

### 4. 新增断言规则类型 `tool_params_contains_any`

被调用工具的参数值里（不区分键名）出现任一指定词。必要性：两个模型用了 `content` / `text` / `message` 三种键名，键名级断言无法通用。

它的实战价值在 MiniMax CP60 上立刻兑现：MiniMax 在无记忆条件下真的调了 message.send，但 content 是自己编的三条要点，与授权内容无关。只看"是否调用了 send"会误判为通过，参数级断言精确抓住了"动作做了但内容错"这个此前不可见的失败类型。

### 5. 两模型的废题集合不重叠

DeepSeek 废题 CP11，MiniMax 废题 CP46。同一套题在两个模型上被判出的废题不同，说明单次运行的废题/陷阱未触发判定受采样噪声影响较大，需要 P1-1 的多次重复才能给稳定的准入结论。
